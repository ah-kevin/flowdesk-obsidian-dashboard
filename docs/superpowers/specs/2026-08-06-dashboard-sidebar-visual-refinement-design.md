# FlowDesk Dashboard 侧栏视觉与交互精细化设计

## 背景

Dashboard 0.1.5 已完成 SDD v3 Parent/Leaf 信息结构、渐进展开、首次加载修复和诊断跳转，但真实 Obsidian 侧栏中的呈现仍然偏向普通网页：标题、按钮、状态卡、子任务卡和合同卡都使用较大的字号、圆角、背景与边框，多个区域拥有近似视觉权重。结构虽然正确，用户仍需要在过长的页面中分辨“当前任务、主要问题和可执行入口”。

实际截图还暴露出两个具体问题：

- 360–420 px 的窄侧栏里，长标题与“复制 CLI”“刷新”按钮争抢同一行，标题容易占据三行以上。
- 技术诊断虽然被移动到详情层，却仍平铺“任务、位置、字段路径”等重复字段；信息完整但缺少细腻的信息层级。

本轮不重新设计数据模型，而是针对 Obsidian 右侧栏完成一次视觉密度和交互语义的精细化，使现有 SDD v3 信息结构真正适合窄栏持续使用。

## 目标

- 在 360–420 px 侧栏宽度内，让首屏优先呈现当前任务、数据可信度和主要诊断。
- 将视觉层级从“多个等权卡片”收敛为“一个主动作、若干轻量摘要”。
- 让 Parent 的直接子任务成为可快速扫描的列表，而不是重复的大卡片。
- 让诊断标题直接说明真实问题，并能跳转到可修正的位置。
- 技术诊断默认只展示实际、预期和修复建议，机器标识按需展开。
- 保持 schema 3 task-centric、fail-closed、同一 snapshot JSON 数据源和只读 Dashboard 约束。

## 非目标

- 不修改 FlowDesk Plugin snapshot producer、SDD v3 判定规则或 JSON contract。
- 不修改 TaskNotes Markdown、task 状态或证据内容。
- 不重新引入 legacy、v1 或 v2 兼容。
- 不加入可配置主题、密度设置或持久化布局偏好。
- 不把 Dashboard 变成合同全文编辑器。

## 设计方向

采用“扁平紧凑控制台”方向：保留一个有明确行动意义的主诊断面板，其余区域主要使用分隔线、文字层级和少量状态色组织。放弃为每个区域增加独立背景、粗边框、左侧色条和大号胶囊。

相较于“保留现有卡片并缩小尺寸”，这一方向能真正降低首屏长度和视觉噪音；相较于“纯文本极简列表”，它仍保留主诊断的行动焦点和必要的状态区分。

## 侧栏布局基线

- 设计基准宽度为 360–420 px，允许更宽侧栏自然伸展，但不因变宽增加第二列。
- 根容器横向内边距建议为 12–14 px，主要区域垂直间距为 12–16 px。
- 当前任务标题建议使用 15–16 px、约 700 字重、1.3–1.4 行高。
- 正文建议使用 11.5–13 px；辅助信息使用 10–11 px。
- 普通区域主要以 1 px 分隔线组织；只有主诊断保留轻背景和 3 px 状态边。
- 圆角集中在主诊断与小型操作按钮，普通列表行不使用卡片圆角。
- 状态色只表达异常、完成、进行中和数据可信度，不把品牌紫色用于普通正文。

## 信息架构

Dashboard 固定按以下顺序渲染：

1. 当前任务区。
2. 数据与合同状态行。
3. 主诊断或健康摘要。
4. Parent 的直接子任务列表；Leaf 不渲染该区域。
5. 当前任务合同与证据摘要。
6. 完整合同、证据和全部技术诊断。

该顺序沿用现有渐进披露结构，但改变每层的视觉重量。

## 当前任务区

### 标题与工具栏

- 当前任务标题是唯一主标题，最多自然换行，不使用大号 Hero 样式。
- “复制 CLI”和“刷新”改为约 26 px 的图标按钮，使用 tooltip 和 `aria-label` 表达含义。
- 当前任务标题独占完整宽度，不与工具按钮共享同一行。
- 标题下方使用一条元信息行：task 状态、Parent/Leaf 类型和优先级位于左侧；复制 CLI 与刷新位于右侧。
- 元信息标签约 22 px 高，图标按钮约 26 px，高度接近但按钮略强；两者垂直居中，组内间距保持 4–6 px。
- 标签与按钮使用协调的圆角、边框和中性背景；状态标签依靠文字与轻状态色区分，工具按钮依靠图标、hover 和 focus 区分，不形成两套互相竞争的视觉语言。
- task 状态、Parent/Leaf 类型与优先级使用 10–11 px 的轻量标签，减少内边距和背景对比度。
- 侧栏极窄导致元信息行无法容纳时，工具按钮整组换到下一行并保持右对齐；标签可以自然换行，但任何情况下都不得重新占用或压缩标题宽度。

### Parent 上下文

- Leaf 标题上方显示一行 Parent 标题，使用向上箭头表达返回层级。
- Parent 标题单行省略，点击打开对应 Parent TaskNote。
- Parent task 自身不显示重复的 Parent 面包屑。

## 数据可信度与合同状态

将现有大面积“观察可信”卡片改为一行紧凑状态：

- 左侧用绿色状态点和“数据可信”表达 schema、model、source task 已匹配。
- 中间可显示简短来源版本，例如 `snapshot v3`。
- 右侧独立显示“合同有效”或“合同 N 项问题”。
- 数据可信与合同健康是两个不同维度，不能用同一绿色面板把合同异常包装成整体健康。
- 生成时间默认不展示完整 ISO 字符串；放入 tooltip 或技术信息，必要时显示相对时间。
- stale 状态改用琥珀色，并明确显示“上次成功结果”；source mismatch 或跨 task 失败继续 fail closed。

## 主诊断

主诊断是页面唯一保留明确面板背景的内容，固定包含：

- 小型状态标签，例如“需要处理”。
- 真实诊断标题，例如“缺少 Task Contract v3”或“任务目标包含占位内容”。
- 一句原因摘要。
- 诊断标题本身作为唯一的打开与定位入口，并提供明确 hover、focus 和方向图标。

不再使用“当前任务需要处理一项诊断”作为主要可点击标题，因为它不能告诉用户要处理什么。

### 点击与定位

- 主诊断标题点击后直接执行打开与定位，不再增加重复的“打开任务并定位”按钮。
- 已有精确行号时，打开对应 TaskNote 并把编辑器光标定位到该行。
- 只有 section 时，打开对应章节。
- 整个章节缺失时，打开 TaskNote 顶部或 producer 提供的建议插入位置，不伪造精确行号。
- 诊断来自 child 时，直接打开对应 child TaskNote，而不是只在 Parent Dashboard 中展开详情。

健康状态不伪装成主诊断。没有诊断时使用轻量健康摘要，说明数据已读取、来源匹配和检查范围。

## Parent 直接子任务

- 直接子任务使用无卡片背景的列表行，以 1 px 分隔线分组。
- 每行包括状态点、child 标题、一行证据或主要问题摘要和单行状态文本。
- 完成状态保持单行，不使用会在窄栏中纵向换行的大胶囊。
- child 标题或整行点击打开对应 TaskNote。
- 默认不重复展示完整诊断文本、文件路径、Goal、REQ/SCN、Leaf 标记或独立“打开”按钮。
- Parent 只展示 direct children，不复制 child 合同和证据详情。

若 child 存在问题，摘要显示最有行动意义的一条，例如“验证结果缺少证据”；若 child 已可信完成，则显示“证据完整 · 验证通过”。

## 合同与证据摘要

- “当前任务合同与证据”摘要层保持默认展开。
- 区域主要使用上下分隔线，不再渲染为独立大卡片。
- Goal 使用普通文字；缺失时显示“未提供”，但不额外占用警告卡片。
- REQ/SCN、验收、执行、验证、交付使用四个紧凑指标单元，避免多个大号灰色胶囊。
- 诊断数量放在摘要标题右侧，例如“6 项诊断”。
- “展开全部合同、证据与诊断”是区域内部的披露操作，不跳转 TaskNote。

## 技术诊断

### 默认显示

每条技术诊断默认显示：

1. 可点击来源标题。
2. 实际情况。
3. 预期结果。
4. 修复建议。

来源标题规则：

- 当前 task 自身诊断：`Task Contract v3 · 第 1 行`、`Goal · 第 8 行`。
- Parent 中展示 child 诊断：`子任务标题 · Verification Result · 第 41 行`。
- 行号缺失时只显示 section；section 也缺失时显示“任务文件”。

不再单列“任务”和“位置”。来源标题已经同时承担归属、位置和跳转语义。

### 机器详情

以下字段放入每条诊断内部的“机器详情”折叠区：

- diagnostic code。
- 完整 task ID 和文件路径。
- 字段路径。
- 原始 section、line 和 producer 元数据。

“机器详情”默认关闭，使用更弱的字号和颜色。它用于排障与开发，不参与普通修复流程。

## 点击行为总表

| 元素 | 行为 |
| --- | --- |
| Parent 上下文标题 | 打开 Parent TaskNote |
| 当前任务标题 | 打开当前 TaskNote；不增加额外“打开”按钮 |
| child 标题或整行 | 打开对应 child TaskNote |
| 主诊断标题 | 打开诊断所属 TaskNote 并定位 |
| 技术诊断来源标题 | 打开诊断所属 TaskNote 并定位 |
| 展开全部合同、证据与诊断 | 在 Dashboard 内展开或折叠 |
| 机器详情 | 在 Dashboard 内展开或折叠 |
| 状态、类型和优先级标签 | 不可点击 |
| 复制 CLI | 复制当前 task 对应 CLI 命令 |
| 刷新 | 重新获取当前 task snapshot |

所有导航入口必须支持 hover、focus-visible、Enter 和 Space，不能只依赖紫色文字表达可点击。

## Parent 与 Leaf 差异

Parent 与 Leaf 共用顶部、可信度、主诊断和合同组件，但：

- Parent 显示 direct children 列表，不显示 Parent 返回入口。
- Leaf 显示 Parent 返回入口，不显示空 children 区域。
- Parent 的合同摘要只描述 Parent 自己；child 详情由各自 TaskNote 和 Dashboard 管理。
- Leaf 的诊断和证据只描述 Leaf 自己，不复制 Parent 合同。

## 空状态与错误状态

- 当前文件不是 TaskNotes task：清空旧 task 数据，显示紧凑空状态和使用说明。
- 没有活动文件：提示打开一个 TaskNotes task。
- source mismatch、schema 或 model 不兼容：fail closed，不展示旧 task 内容。
- 同 task 刷新失败：可以保留上次成功内容，但顶部状态行必须明显标记 stale。
- 字段缺失：显示“未读取到”或“未提供”，不得默认为零或健康。

空状态仍保留刷新；只有能确定 task path 时才显示复制 CLI。

## 实现边界

- `src/dashboard-presentation.ts` 负责把 snapshot view model 转换为紧凑显示内容和导航目标。
- `src/main.ts` 负责 Obsidian 生命周期、DOM、键盘交互和文件定位。
- `styles.css` 负责侧栏密度、层级 token、窄宽度适配与交互状态。
- 不在 DOM helper 中重新解释 SDD v3 判定逻辑。
- 不要求 producer 新增字段；缺失精确位置时只做保守降级。

## 测试与验收

### 展示模型

- 主诊断标题使用真实问题，不使用泛化的“一项诊断”。
- 当前 task 和 child 来源标题分别遵循规定格式。
- 默认技术诊断不包含独立“任务”“位置”“字段路径”和 diagnostic code。
- 机器详情仍能访问完整诊断事实。
- Parent child 行只包含 direct child 的紧凑摘要。

### DOM 与交互

- 当前任务、Parent、child、主诊断和技术诊断都跳转到正确 TaskNote。
- 有 line 时定位行，无 line 时正确退化到 section 或文件。
- 状态标签不可点击；披露控件只在 Dashboard 内展开。
- 图标按钮有 tooltip、`aria-label` 和键盘焦点。
- 标题始终独占完整宽度；图标按钮只出现在标题下方的元信息行。
- 标签与按钮垂直居中、尺寸协调；窄宽度下工具组整体换行，不遮挡标题，完成状态不纵向断字。

### 回归验证

## 取舍

- 选择扁平列表与分隔线，放弃每段信息都使用独立卡片；减少视觉噪音，但需要依靠稳定的字号与间距 token 建立层级。
- 选择小型图标工具栏，放弃顶部大文字按钮；释放标题空间，但必须提供 tooltip 和无障碍标签。
- 选择工具栏位于标题下方元信息行右侧，放弃与标题同排或独占顶部工具行；标题获得完整宽度，同时避免额外增加一整行顶部留白。
- 选择真实问题作为主诊断标题，放弃统一的泛化标题；行动更直接，但 presentation 层必须为现有诊断提供稳定的人类摘要。
- 选择来源标题合并任务归属和位置，放弃独立“任务/位置”字段；普通用户更易扫描，完整机器事实仍保留在折叠区。
- 选择 Parent 只展示 child 摘要，放弃在 Parent 中复制 child 详情；符合 TaskNotes 原生父子职责并减少重复事实。
- 选择针对 360–420 px 单列优化，放弃宽屏多列布局；Dashboard 的核心宿主是 Obsidian 侧栏，宽屏不是本轮主要场景。

## 上线后观察点

- 首屏是否能在不滚动或少量滚动下看到主诊断和至少一部分 child/合同摘要。
- 用户是否能仅凭诊断标题判断要处理的问题。
- child 列表是否足以支持 Parent 层人工 review。
- “机器详情”的打开频率是否显著低于原技术诊断详情。
- 360 px 窄栏中的标题换行、状态文本和操作按钮是否稳定。
- 首次打开、文件切换和刷新时是否仍会出现空白、旧数据或展开状态跳变。
